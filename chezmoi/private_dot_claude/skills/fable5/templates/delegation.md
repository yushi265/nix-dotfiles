# 委譲・オーケストレーションモード

自分で作業する代わりに、サブエージェント（別モデル含む）へ作業を切り出すときの手順。
**委譲しても、成果物の品質責任は委譲した側に残る。**
（この型は 2026-07-03 の ZenWork 開発セッションで Fable 5 が実際に使った委譲プロンプト4通から抽出したもの）

## 適用場面

- 実装を別モデル（例: Sonnet）に任せ、自分は設計と検証に専念する運用
- 独立した調査・レビュー・実装を並列で走らせたいとき
- コンテキストを消費する大きな読み込み作業を切り出したいとき
- 目安: 委譲は「仕様が固まった実装」「範囲が定義できる調査」に向く。**文書・計画・設計の執筆は委譲せず自分で行う**（Fable 5 の実ログ観察より: 計画局面では Edit 131回を自分で行い、委譲は4回のみ）

## 委譲前の準備

- **曖昧さは委譲前に潰す。** 仕様が曖昧なまま投げると、サブエージェントは勝手に補完する。設計判断は委譲側で済ませ、実装だけを切り出す
- サブエージェントは**コンテキストゼロ**で始まることを前提に、必要な文脈をプロンプトに全部入れる（会話の暗黙知は伝わらない）

## 委譲プロンプトの必須構成（8項目）

1. **タスクの本質＋文脈** — 1行目に「何のプロジェクトの何をするか」（例:「zen-todo の後継、manifest id: zen-work」）
2. **必読ファイル** — パスだけでなく「なぜ読むべきか」を添える（例:「parser/markdown-serializer.ts（互換性維持の要。必ず読むこと）」）
3. **背景の核心の要約** — 設計の要点を短く言語化して渡す（例:「このドキュメントモデルは『編集していない行は1バイトも変えない』」）
4. **具体的な仕様** — 実装ならシグネチャ・型レベルまで（例:「mapZenTodoSettings(raw: unknown): Partial<ZenTodoSettings> — 純粋関数」）
5. **変更禁止範囲＋回避手順** — 禁止だけでなく、触りたくなった時の行動まで指定（例:「既存ファイルの変更禁止。手を入れたくなったら、その理由を報告に書いて手を入れずに回避策を取る」）
6. **権限の制限** — 逸脱されて困る操作を明示（例:「git 操作（add/commit/stash）禁止」「外部送信禁止」）
7. **検証可能な完了条件** — 機械的に判定できる形（例:「`pnpm test` 全緑（既存130テストを壊さない）、`pnpm build` 成功」）
8. **報告形式の指定** — 何を報告させるか（例:「作成ファイル一覧、テスト数と結果、採用したアルゴリズムの要約、設計上の判断や気づいた問題点」）

補助: スコープ外も明示する（「旧パーサ自体の問題は指摘不要」「挨拶や前置きは不要」）。レビュー委譲なら重大度分類（CRITICAL/HIGH/MEDIUM/LOW）とファイルパス:行番号を要求する。

## 並列ファンアウト（大規模な調査・監査を委譲するとき）

対象が大きい調査・監査は、1エージェントで舐めずに並列分割する（実例: 2026-07-03 文書監査で19エージェント並列）:

- **2軸で分割する**: 範囲別（ディレクトリ・文書グループごと）＋**横断観点別**（命名整合・役割定義・バージョン間整合など）。範囲軸だけだと「どの担当範囲にも属さない横断矛盾」を取りこぼす
- エージェントには**担当が分かる名前**を付ける（例: `audit-g1-specs`, `audit-x1-naming`）。進捗把握と結果の突合が楽になる
- 報告フォーマットは**カバレッジ3点セット**で固定する:
  1. **指摘**（重大度・出典付き）
  2. **問題なしと確認した観点** — 指摘ゼロ≠安全。「何を見て問題なしとしたか」を書かせる
  3. **未確認範囲** — 時間・権限・情報不足で見ていないもの
- 回収時は**完全な報告を要求**する（「省略せず全指摘を含めて送れ」）。サブエージェントは放っておくと要約して情報を落とす
- 一発委譲で終わりにせず、必要ならスポーン後も対話（SendMessage 等）で追加指示・確認・回収をする

## 裁定の返し方（委譲した調査で矛盾・分岐が見つかったら)

- 矛盾の正は自分で決めない（仕様の価値判断）。**対立の構図を整理して人間に裁定させる**: 「文書AはXと言い、文書BはYと言う。どちらを正としますか」＋自分の推奨
- 裁定事項が複数あるなら番号を振り（D-1, D-2, …）、**まとめて一度に**聞く（小出しにしない）

## 委譲後の検証（省略禁止）

- **自己申告を信用しない。** 「完了しました」「全部適用しました」は必ず独立に検証する:
  - 差分を自分の目で読む（禁止範囲への変更・頼んでいない変更の混入チェック）
  - テスト・ビルドを**自分で再実行**する（申告された結果の鵜呑み禁止）
  - git 状態を確認する（勝手な git 操作の検出）
- リスクの高い変更は、修正後に**検証専用のレビューをもう1周**かける（1周目の指摘への「修正」自体に新たな見落としが生じることがある）
- サブエージェントが報告した「問題点・設計判断・気づき」は、自分の完了報告に引き継ぐ（握りつぶさない）

## 完了条件

- [ ] 委譲プロンプトに8項目が揃っていた
- [ ] 完了条件を自分で再実行して確認した（申告の鵜呑みでない）
- [ ] 差分に禁止範囲への変更・頼んでいない変更が無いことを確認した
- [ ] git 状態に想定外の操作痕跡が無いことを確認した
- [ ] サブエージェントの報告した問題点・判断を自分の完了報告に引き継いだ
