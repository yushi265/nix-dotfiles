# リファクタリングモード

**外部から見た振る舞いは一切変えない。** 機能追加・バグ修正を混ぜない。

## 着手前に揃える情報

| 情報 | 欠けていたら |
|------|-------------|
| 対象（ファイル/モジュール/関数） | ユーザーに確認（これが無いと作業できない） |
| 動機（重複排除、次の機能追加の準備、可読性など） | 会話から推定し宣言。動機で「どこまでやるか」が決まるため、不明瞭なら確認 |
| ゴールの形（パターン、分割方針） | 既存コードの慣習から自分で提案し、計画で提示 |
| やらないこと（スコープ外） | 「命名変更・public API・依存更新は対象外」を既定とし、計画で宣言 |

## 作業手順（Martin Fowler 流）

1. 対象コードと**その呼び出し元をすべて読み**、現在の振る舞いを把握する
2. **テストの網を確認する**: 対象の振る舞いを保護するテストが十分にあるか確認。不足していれば、リファクタリング前に現在の振る舞いを固定するテストを追加する（振る舞いを変えないので先行してよい）
3. 全テストを実行しグリーンを確認する（開始地点の確定）
4. **小さいステップで進める**: 1ステップ = 1つの変形（メソッド抽出、移動、インライン化など）。**各ステップ後にテストを実行**する
5. テストが落ちたら**直前のステップを巻き戻す**。落ちたまま次のステップに進まない
6. 全体完了後、全テスト・lint・ビルドを実行する
7. 完了報告（結果 / 変更点 / 検証 / 未検証・仮定・提案）

## 完了条件

- [ ] 全テストが変更前と同じく通る（実行出力を提示）
- [ ] 外部から見た振る舞い・public API が変わっていない
- [ ] 機能追加・バグ修正が混ざっていない（気づいたバグは報告のみ）
- [ ] 各ステップが説明可能（どんな変形を適用したか列挙できる）
