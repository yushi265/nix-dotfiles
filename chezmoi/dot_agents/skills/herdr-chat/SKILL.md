# herdr-chat — 別ペインのセッションと会話する

herdr のペインを1枚増やして Claude セッションを立て、議題を投げ、応答を回収し、**最後に必ずペインを閉じる**。

CLI の詳細仕様が必要になったら `~/.claude/skills/herdr/SKILL.md` を Read する（このスキルでは重複させない）。

## 重要な前提

- **herdr のソケット API はサンドボックス内から呼べない。** `herdr` のサブコマンド実行は
  すべて `dangerouslyDisableSandbox: true` で行う。サンドボックス内だと
  `Error: Os { code: 1, kind: PermissionDenied }` で失敗する。
  ヘルプ表示（`herdr pane` など引数なし）だけはローカル完結なので通る。
- ペインIDは**必ず JSON レスポンスから読む**。例や勘で組み立てない。

## 手順

### 0. 前提チェック

```bash
test "${HERDR_ENV:-}" = 1
```

失敗したら「herdr のペイン内で動いていないので実行できない」と伝えて**停止する**。
外部から herdr セッションを操作しない。

自分の位置を確認する:

```bash
printf '%s\n' "$HERDR_WORKSPACE_ID" "$HERDR_TAB_ID" "$HERDR_PANE_ID"
```

### 1. 議題とモデルを決める

**議題**

- **引数がある場合** → その内容が議題。これをそのまま相手に投げる。
  勝手に要約・言い換え・タスク分解をしない。
- **引数がない場合** → 「何について話させたいか」をユーザーに1回だけ聞く。
  直前の会話の文脈から議題が明らかなら、それを宣言して進めてよい。

**エージェント種別（kind）**

引数から相手のエージェント種別を抽出する。「codex で」「codex に聞いて」のような
自然文でも、`codex` という単独トークンでも受け付ける。
**指定がなければ `claude`** を使う。

`claude` と `codex` 以外を指定されたら、`herdr agent` で対応 kind 一覧を確認し、
存在すればそれを使う。存在しなければユーザーに伝えて止まる。

**モデル**

引数からモデル指定を抽出する。次のいずれの書き方も受け付ける:

- `--model fable` / `--model claude-fable-5` のようなフラグ形式
- 「fable で」「sonnet に聞いて」「opus で壁打ち」のような自然文

抽出した種別・モデル指定は**議題から取り除く**（相手に渡すプロンプトに混ぜない）。
モデル指定がなければモデルフラグを付けずに起動し、相手はその CLI の既定モデルで動く。

**モデルフラグは kind ごとに違う。取り違えると起動に失敗する:**

| kind | フラグ | 受け付ける値 |
| --- | --- | --- |
| `claude` | `--model` | エイリアス（`fable` / `opus` / `sonnet` / `haiku`）またはフルネーム（`claude-fable-5` 等） |
| `codex` | `-m` (`--model`) | codex 側のモデル名 |

ユーザーが書いた表記をそのまま渡し、勝手に別のモデルへ読み替えない。
指定が実在するモデルか判断できないときは、起動前にユーザーへ確認する。
kind とモデルの組み合わせが矛盾する場合（例: `codex` に `opus`）も確認する。

抽出した kind とモデルは、そのままコマンドに埋めずに**書式を検証する**。
`kind` は `herdr agent` が挙げる既知の kind と完全一致すること。
モデル名は英数字・ハイフン・ドット・アンダースコアのみで構成されること。
空白や引用符、`;` `|` `&` `$` `` ` `` などのシェルメタ文字を含む値は**使わない**。
検証を通らなければユーザーに確認する。コマンドに渡すときは必ずクォートする。

議題が決まったら、相手セッションに渡すプロンプトを組み立てる。先頭に文脈を1行だけ添える:

```
（別ペインの Claude セッションからの依頼です）
<議題>
```

**相手は同じ作業ディレクトリで、書き込み権限を持って動く。**
指示の受け取り方によっては自律的にファイルを編集する。
そのため、**ユーザーが実装・修正を明示的に依頼していない限り、
「ファイルは変更しないでください」をプロンプトに必ず含める。**
相談・レビュー・調査・壁打ちはすべて「変更しない」側である。
ユーザーが実装を依頼している場合だけ、この一文を外す。

相手は**独立したコンテキスト**を持つ。こちらの会話履歴は一切見えないので、
議題の理解に必要な背景（対象ファイル・前提・期待する出力形式）は
プロンプトに明示的に含めること。

### 2. ペインを分割する

分割方向は呼び出し元ペインの形状で決める:

```bash
herdr pane layout --pane "$HERDR_PANE_ID"
```

`.result.layout.panes[]` から **`pane_id` が `$HERDR_PANE_ID` と一致する要素**を選び、
その `rect` を読む。`focused: true` や `.result.layout.focused_pane_id` で選んではいけない
（フォーカスされているのはユーザーや他クライアントのペインでありうる）。

`rect.width` は桁数、`rect.height` は行数。これで方向を決める:

- `width` が **160 以上** → `--direction right`（分割後も各 80 桁前後を確保できる）
- それ未満 → `--direction down`

ユーザーが方向を指定していればそちらを優先する。ただし分割後に

- 幅が **70 桁未満**、または
- 高さが **20 行未満**

になる分割はしない。第一候補の方向が下限を割っても、**もう一方の方向が下限を満たすなら
そちらを使う**（例: `width 150 × height 30` は `down` だと 15 行になるので `right` を選ぶ）。
**両方向とも下限を割る場合だけ**、分割せずに停止して
「今のペインが小さすぎて分割できない」とユーザーに伝える。

フォーカスは奪わず、カレントの作業ディレクトリを引き継ぐ:

```bash
herdr pane split --current --direction right --cwd "$PWD" --no-focus
```

**`.result.pane.pane_id` を控える。** 以降の操作と後片付けで使う。

`split` が成功したのに応答を取り損ねた場合（pane_id が分からない）、
そのままにすると孤児ペインが残る。`herdr pane list --workspace "$HERDR_WORKSPACE_ID"` を取り、
**この手順の冒頭で実行した `pane layout` の応答に無かったペイン**を差分で特定する。
そのうえで「自分のタブ `$HERDR_TAB_ID` にある」「`agent` フィールドを持たない
（＝エージェントが載っていない）」の両方を満たすものだけを閉じる。
1つに絞り込めなければ閉じずに、ペイン一覧を添えてユーザーに報告する。

### 3. エージェントを起動する

エージェント名は `[a-z][a-z0-9_-]{0,31}` に従い、議題が分かる名前を付ける
（例: `review-auth`, `bench-idea`）。名前は**全ワークスペース横断でライブなエージェント全体**に
対して一意でなければならない。衝突を確認する:

```bash
herdr agent list
```

同名が既に居たら、**その名前は使わない**。接尾辞を足すなどして別名にする。
既存エージェントのリネームや停止は絶対にしない（他人の作業を壊す）。

起動する。エージェントの起動は数十秒かかることがあるので、既定の 30 秒ではなく余裕を持たせる:

```bash
herdr agent start <name> --kind <kind> --pane <控えた pane_id> --timeout 120000
```

モデル指定がある場合は、**`--` の後ろ**に native 引数として渡す
（`--` より前に置くと herdr 自身のオプションとして解釈されて失敗する）。
フラグは kind ごとに違う:

```bash
# claude
herdr agent start <name> --kind claude --pane <pane_id> --timeout 120000 -- --model fable
# codex
herdr agent start <name> --kind codex  --pane <pane_id> --timeout 120000 -- -m <model>
```

`agent_status` が `idle` かつ `interactive_ready: true` で返れば**起動完了の候補**。
ただしこれだけで入力を受け付けると断定しない。起動途中や、検出はできたが未 ready の
状態もありうる。次の「起動直後のモーダル確認」で画面を実際に読み、
入力プロンプトが出ていることを目視で確かめてから手順4へ進む。

`agent_status` が `unknown` で返った場合は、herdr がエージェントを分類できていない。
**完了の証拠にはならない。** 画面を読んで判断し、判断できなければユーザーに報告する。

**起動に失敗した場合** — `agent start` はエラー JSON を返す。
`{"error":{"code":"timeout"}}` 以外のコードもありうるので、`error` キーの有無で判定し、
`code` と `message` をそのまま報告に使う。
失敗した pane にはエージェントが載っていないため `herdr agent read` は
`agent_not_found` になる。原因は **`agent` 系ではなく `pane` 系**で読む:

```bash
herdr pane read <pane_id> --source visible --lines 40
```

`--source recent-unwrapped` は空を返すことがあるので、失敗診断では `visible` を使う。
ここに CLI 側の起動エラー（コマンドが見つからない、バイナリが壊れている等）が出る。
**原因を読み取ったうえで**、手順7に従ってペインを閉じ、そのあとで原因を報告する。
原因を確認せずに再試行しない。

> **以降のターゲットには、エージェント名ではなく控えた `pane_id` を使う。**
> `agent` 系コマンドは名前と pane_id のどちらも受け付けるが、名前は
> ライブなエージェント全体で解決されるため、衝突や `start` 失敗を見落とすと
> **他ワークスペースの他人のセッションに議題を投げ込む**危険がある。
> pane_id は自分が作ったペインを一意に指すので、この事故が起きない。

モデル指定があった場合のみ、意図したモデルで動いているか確認する:

```bash
herdr agent read <pane_id> --source visible --lines 10
```

多くの CLI はステータス行にモデル表示を出す（Claude Code なら例: `Fable 5`）。
指定したエイリアスと表示名は綴りが一致しないので、**同じモデル系列を指しているか**で判断する。
表示位置や有無は CLI ごとに違うので、出ていないこと自体は異常ではない。

- 明らかに別モデルだった → **1 回だけ**やり直す。やり直しは
  「今のペインを `herdr pane close` で閉じる → 手順2からやり直して新しいペインを作る →
  `.result.pane.pane_id` を**新しい値に控え直す** → 手順3で名前の衝突を再確認して起動」
  の順で行う。古い pane_id を使い回さない
- 2 回目も違う、または表示が読み取れず照合できない → **やり直さず**、
  観測した内容を添えてユーザーに報告して指示を仰ぐ

ステータス行の表示内容はユーザーの statusline 設定に依存するため、
読み取れないこと自体は異常ではない。同じ操作を繰り返さないこと。

別のエージェント種別を使いたいと言われたら `--kind` を変える（`herdr agent` で一覧を確認）。
`--kind` によって native 引数は変わるので、`claude` 以外では `--model` が通るとは限らない。

**起動直後のモーダルを必ず確認する。** これを飛ばすと最初の議題が消える:

```bash
herdr agent read <pane_id> --source visible --lines 30
```

`agent start` が `idle` / `interactive_ready: true` を返しても、CLI が起動時の確認
ダイアログを出していることがある（codex の hooks 承認画面など）。この状態で
`agent prompt` を投げると、テキストがモーダルに吸われて**エラーなしで `idle` が返る**。
届いていないことに気づけないまま「応答なし」と誤解する。

モーダルが出ていたら、まず `esc` を送る:

```bash
herdr agent send-keys <pane_id> esc
```

**`esc` で閉じるとは限らない。** 同じ CLI でも版や状況で形式が変わる。
実際に確認されている 2 形式:

| 形式 | 表示 | `esc` の意味 |
| --- | --- | --- |
| ヒント型 | `Press t to trust all; enter to review; esc to close` | 閉じる |
| メニュー型 | `1. Review / 2. Trust all / 3. Continue without trusting` + `esc to go back` | **戻る**（戻り先がなければ閉じない） |

`esc` を送ったら、少し待ってから**もう一度画面を読んで**閉じたか確認する。
描画が遅れて残って見えることがあるので、1 回の読み取りで判断しない。

閉じなかった場合:

- **信頼・承認を与える選択肢（`Trust all`、`t` など）は絶対に選ばない。**
- 「信頼せずに続行」に相当する選択肢があっても、**自分の判断で確定しない。**
  何も与えない選択に見えても、相手 CLI の以後の挙動を変える設定変更でありうる。
- 選択肢の一覧をそのままユーザーに提示して、どれを選ぶか指示を仰ぐ。

**確定キー（`enter`）は、カーソル位置を読んで意図した選択肢にあると確認できるまで送らない。**
カーソル位置が読み取れないなら送らない。

閉じたあと、入力プロンプトが出ていることを確認してから手順4へ進む。

### 4. 議題を投げて待つ

```bash
herdr agent prompt <pane_id> '<組み立てたプロンプト>' --wait --timeout 300000
```

- テキストはシングルクォートで囲む。中にシングルクォートが含まれるなら `'\''` でエスケープする。
- `--wait` だけで `idle` / `done` / `blocked` の落ち着いた状態まで待つ。
  `--until` は特定状態を狙うとき以外つけない。
- 調査やレビューを伴う議題は数分かかる。タイムアウトは短く見積もらない。
- **`idle` が返っただけでは「応答した」と判断しない。** 手順5で画面を読み、
  投げた議題が実際にエコーされ、それに対する応答が続いているかを確認する。
  議題が見当たらないなら届いていない（モーダルに吸われた等）。
  その場合は手順3のモーダル確認に戻ってから投げ直す。

返り値ごとの分岐:

| 状況 | 対応 |
| --- | --- |
| `idle` / `done` | 応答完了。手順5へ |
| `blocked` | 相手が承認待ちか質問中。下の「承認プロンプトへの対応」に従う |
| `agent_prompt_stalled` | 相手が入力を受け付けていない。`herdr agent get <pane_id>` と `agent read` で状況を見てから判断する |
| タイムアウト（まだ `working`） | **絶対に再プロンプトしない。閉じもしない** |

タイムアウト時に同じテキストをもう一度投げると、作業中のセッションに文字列が
注入されて相手の応答が壊れる。ペインを閉じれば作業ごと失われる。待ち直す:

```bash
herdr agent wait <pane_id> --timeout 300000
```

待ち直しても終わらない場合は、経過と現在の状態をユーザーに報告して指示を仰ぐ。
そのときは手順7の「閉じずに待つ場合」の申し送りを必ず書く。

### 承認プロンプトへの対応（`blocked` のとき）

相手 CLI は、コマンド実行のたびに承認を求めてくることがある（codex の既定がこれ）。
毎回ユーザーに聞くと実用にならないので、**コマンドを機械的に検査して読み取り専用のものだけ
自動承認する**。判断は目視の印象ではなく、下の3段ゲートとの照合で行う。

> **これはセキュリティ境界ではない。** 端末画面のテキストを検査しているだけで、
> alias / shell function / PATH の乗っ取り / 環境変数 / 設定ファイル / glob 展開後の
> 実 argv までは検査できない。読み取りから確定キー送信までに画面が変わる余地（TOCTOU）も、
> 端末制御シーケンスで偽の承認画面を描かれる余地もある。
> **これはプロンプト疲れを減らすための保守的なフィルタであって、
> 本当の防御は相手 CLI 側のサンドボックス設定**（codex なら `sandbox_mode` / `approval_policy`）
> にある。迷ったら承認しない。ここで守り切れると考えない。

まず何を求められているか読む:

```bash
herdr agent read <pane_id> --source visible --lines 40
```

承認ダイアログなら、実行しようとしているコマンド行を抜き出し、
**次の①→②→③の順**で照合する。1つでも通らなければ承認しない。

#### ① 構文ゲート

次の文字・記法を1つでも含めば承認しない:

```
|  ;  &  &&  ||  >  >>  <  $(  ` )  改行
*  ?  [  ~  {  }        ← glob・ブレース展開
```

パイプ・連結・リダイレクト・コマンド置換・サブシェルを含む複合コマンドは、
先頭が読み取り専用コマンドでも中身は何でもできる。**単一コマンドでなければ承認しない。**

glob を弾くのは、**画面に表示されたコマンドと実際に実行される argv が一致しなくなる**ため。
`rg needle *` は、ディレクトリに `--pre=sh` という名前のファイルがあれば
`rg needle --pre=sh ...` に展開されうる。表示上は危険オプションが見えない。

#### ② 停止リスト

1つでも当たれば承認しない。即停止し、コマンド全文を添えてユーザーに判断を仰ぐ:

- 「今後確認しない」「don't ask again」「Trust all」など**恒久的な権限付与**
- herdr の状態変更系: `pane close` / `split` / `run` / `send-text` / `send-keys` /
  `move` / `swap`、`agent start` / `prompt` / `send-keys` / `rename`、
  `server stop`、`tab create` / `close`、`workspace create`、`worktree`
- ファイル書き込み・削除・権限変更: `rm` / `mv` / リダイレクト / `tee` / `chmod` / `chown`
- ネットワーク・外部影響: `curl` / `ssh` / `npm` / `git push` / `git commit` などの履歴書き換え
- **`sed` / `awk` / `find` / `xargs`** — すべて書き込みか任意実行の経路を持つ
  （`sed -n 'w out.txt' in.txt` は `w` でファイルを書く。再現確認済み）
- `printf -v` — シェル変数への代入。読み取り専用ではない

#### ③ 許可リスト

①②を両方通った場合のみ、次に**完全一致**するものを自動承認する:

| コマンド | 追加条件 |
| --- | --- |
| `herdr pane layout` / `list` / `get` / `read` / `current` / `edges` / `neighbor` / `process-info` | — |
| `herdr agent list` / `get` / `read` / `explain`、`herdr workspace list`、`herdr tab list` | — |
| `cat` / `head` / `tail` / `ls` / `wc` / `echo` | 引数は素のパスとフラグのみ |
| `printf` | `-v` を含まないこと（②で停止） |
| `rg` / `grep` | **`--no-config` が付いていること**。`--pre` / `--pre-glob` / `--hostname-bin` / `-f` / `--file` / `-z` / `--search-zip` を含まないこと |
| `herdr` / `claude` / `codex` の `--help` / `--version` | **これら既知のコマンド名そのもの**に限る。`/` を含むパス指定（`./evil --help` 等）は不可 |

`rg` に `--no-config` を要求するのは、`RIPGREP_CONFIG_PATH` の設定ファイルに
`--pre=sh` が書かれていれば、表示コマンドに危険オプションが無くても実行されるため。
`-z` / `--search-zip` は `gzip` などの外部プログラムを PATH から起動する。

**表に無いコマンドは承認しない。** 判断に迷うオプションが1つでもあれば承認しない。
「たぶん読み取り専用」で通さない。

#### 確定キーの送り方

自動承認するときは、**カーソルが「1回だけ許可」の選択肢にあることを画面で確認してから**
確定キーを送る。カーソルが別の選択肢にある、または位置が読み取れない場合は、
**確定キーを送らずに停止**してユーザーに聞く（矢印キーで動かして合わせようとしない。
選択肢の並びは CLI ごとに違い、動かした先が「Trust all」でありうる）。
**「今後確認しない」側は絶対に選ばない。**

確認した画面と確定キー送信の間に画面が変わる可能性は消せない。
**確定キーを送ったあとも、何が実行されたかを画面で確認する。**
意図と違うものが実行されていたら、その時点でユーザーに報告する。承認後は再び待ち直す:

```bash
herdr agent send-keys <pane_id> enter
herdr agent wait <pane_id> --timeout 300000
```

承認は連続して発生する。上限（20 回程度）を決めてループし、
上限に達したら停止してユーザーに報告する。

**承認したコマンドは 1 件残らず記録し、手順8の報告に全件載せる。**
「読み取り専用だったので省略」は禁止。

承認ダイアログではなく**相手からの質問**だった場合は、自動で答えない。
質問内容をユーザーに伝えて指示を仰ぐ。

### 5. 応答を回収する

```bash
herdr agent read <pane_id> --source recent-unwrapped --lines 150
```

- ログ・応答文の回収には `recent-unwrapped` を使う（ソフトラップが結合される）。
- `--lines` を増やしても応答の先頭が取れない場合、相手が代替スクリーンで描画している。
  そのときだけフォールバックとして「応答全文を一時ディレクトリに Markdown で書き出し、
  パスだけ返して」と追加で頼み、そのファイルを直接 Read する。
  最初のプロンプトでファイル出力を要求してはいけない。

  このフォールバックは手順1の「ファイルは変更しないでください」と衝突する。
  **依頼するときは例外の範囲を明示する**こと:
  「作業対象のファイルは引き続き変更しないでください。応答の書き出し先は
  一時ディレクトリ配下の新規ファイルだけにしてください」と添える。
  既存ファイルへの上書きやリポジトリ内への書き出しは依頼しない。

**回収に失敗したときの分岐:**

| 症状 | 意味 | 対応 |
| --- | --- | --- |
| `agent_not_found` が返る | 相手が終了した／ペインから消えた | `herdr pane read <pane_id> --source visible` で終了時の出力を読む。回収できた分だけ報告し、手順7で閉じる |
| `agent read` は通るが本文が空 | ソースの選択ミス、または描画待ち | `--source visible` に切り替えて読み直す。それでも空なら少し待って再読 |
| `agent_status` が `unknown` のまま | herdr が分類できていない。**完了の証拠にはならない** | 画面を読んで実際に応答が出ているか確認する。判断できなければユーザーに報告 |
| ペイン自体が消えている（`pane get` も失敗） | プロセスごと落ちた | 回収は諦め、落ちた事実と直前に観測した内容を報告する。閉じる対象も無いのでその旨も書く |

いずれの場合も、**取れなかったものを取れたことにしない。**
部分的にしか回収できなかったなら「ここまでしか読めなかった」と明示して報告する。

### 6. 続きのやり取り（必要な場合のみ）

追加で聞きたいことがあれば 4→5 を繰り返す。相手のセッションは**継続している**ので、
前のやり取りを踏まえた質問ができる。

```bash
herdr agent prompt <pane_id> '<追加の質問>' --wait --timeout 300000
herdr agent read <pane_id> --source recent-unwrapped --lines 150
```

### 7. ペインを閉じる（必須。報告より先に行う）

応答を回収し終えたら、**ユーザーに報告する前に**片付ける:

```bash
herdr pane close <控えた pane_id>
```

**報告を先にしてはいけない。** 報告文をそのターンの最終応答にすると、そこでターンが
終わってこの手順が実行されず、ペインが残ったままになる。閉じてから報告する。

- これは相手セッションのプロセスごと終了させる。回収し残しがないか確認してから実行する。
- **手順の途中で失敗・中断した場合も閉じる。** 起動失敗、ユーザーの中止指示、
  分割はできたが起動に失敗した、いずれの場合も作りかけのペインを残さない。
- **ただし相手がまだ `working` の間は、自分の判断で閉じない。** 作業ごと失われる。
  手順4のとおり `agent wait` で待ち直す。
  自分の判断で閉じてよいのは、応答を回収し終えたか、相手が動いていないと確認できたときだけ。
  **ユーザーが明示的に中止・終了を指示した場合は `working` でも閉じる。**
  その際は「作業途中で打ち切った」ことを報告に添える。
- **閉じずにユーザーの回答を待つ場合**（`working` のまま終わらない、承認判断を仰ぐ、
  許可リスト外のコマンドで停止した等）は、報告に必ず
  **ペインID・エージェント名・現在の状態**を明記し、
  「次のターンで必ず閉じる」ことを自分への申し送りとして書く。
  これを書かないと、会話がそこで途切れたときにペインが孤児化する。
- 閉じたことを報告に含める。
- **例外**: ユーザーが「残しておいて」と明示した場合のみ残す。
  その場合もペインIDとエージェント名を報告し、後で閉じられるようにする。
- 自分が作っていないペイン・タブ・ワークスペースは**絶対に閉じない**。

### 8. 報告する

ユーザーには次を伝える:

- **相手の回答内容**（要点。長ければ要約しつつ、判断に効く部分は原文のまま）
- こちらの見解との**一致点・相違点**（相違があれば、どちらが正しいか自分で決めずに対立の構図を示す）
- 相手が置いた**前提や留保**
- **「承認プロンプトへの対応」で承認したコマンド全件**（1件も省略しない）
- ペインを閉じたこと。閉じていないなら、その理由とペインID

相手の回答を無検証で正としない。事実関係は自分で裏取りする。
特に「行番号つきの指摘」は、実際にその行を読んでから採否を判断する。

## やらないこと

- ワークスペースやタブの新規作成（ユーザーが明示的に要求したときだけ）
- `--focus` でのフォーカス奪取（ユーザーが「切り替えて」と言ったときだけ）
- `herdr server stop` / メインプロセスの kill
- 「承認プロンプトへの対応」の許可リストを超えた承認（書き込み・ネットワーク・trust・恒久付与）
