# 設計レビューモード

成果物はレビューコメント。**コードは書かない。**

## 着手前に揃える情報

| 情報 | 欠けていたら |
|------|-------------|
| 設計文書 / 提案内容 | ユーザーに確認（これが無いと作業できない） |
| 解決したい課題 | 文書・会話から読み取り、自分の言葉で要約して認識を提示 |
| 前提・制約（チーム規模、期限、既存システム、性能要件） | 文書と vault・コードベースから調べる。重要な空白は「前提として確認したい」に列挙 |
| 判断してほしい点（例: A案とB案どちらか） | 未指定なら「設計全体の妥当性評価」として進める |

## 作業手順

1. 解決したい課題を自分の言葉で要約し、認識を提示する
2. **関連する既存コード・既存設計を実際に読み**、設計が現実のコードベースと整合するか確認する
3. 以下の観点で評価する:
   - **課題適合**: この設計は本当に課題を解くか。過剰設計/過小設計でないか
   - **整合性**: 既存のアーキテクチャ・パターン・規約と衝突しないか
   - **リスク**: 失敗しうる点、単一障害点、スケール限界、移行の難所
   - **代替案**: より単純な案で足りないか（「何もしない」案も含めて比較）
   - **可逆性**: あとで方針転換できるか。できない決定はどれか
4. **不可逆な決定**（データスキーマ、公開API、技術選定）と可逆な決定を区別し、不可逆なものを重点的に検証する
5. 結論を出す: **賛成 / 条件付き賛成（条件を列挙） / 反対（代替案を提示）**

## 完了条件

- [ ] 課題への適合性を評価した（設計の綺麗さだけを見ていない）
- [ ] 既存コードベースとの整合を実際にコードを読んで確認した
- [ ] 不可逆な決定が列挙され、それぞれ検証されている
- [ ] 明確な結論（賛成/条件付き/反対）と根拠がある
- [ ] 確信が持てない点は「要確認」として区別されている
