# fable5 — タスク実行フレームワーク

開発タスクを「プロトコル読込 → 種別判定 → テンプレート読込 → 手順実行 → 完了条件突合」の流れで遂行する。
共通の行動規範（protocol.md）と、その上に載る「タスク種別ごとの手順書」（templates/）を提供する。

## 手順

### 0. 共通プロトコルを Read する

共通の行動規範（質問/行動の判断フロー・要求チェックリスト・2ストライクルール・4部構成報告など）は
[protocol.md](protocol.md) に定義されている。**必ず最初に Read し**、以降のすべての手順でこれに従う。
例外: 常時適用モードで導入済みの環境（同内容の `.claude/rules/fable5-protocol.md` が
既にコンテキストへ自動読み込みされている場合）は、再度 Read せずそれに従えばよい。

### 1. タスク種別を判定する

依頼内容から下表で種別を判定し、**どの種別として扱うかを冒頭で宣言**する。

| 種別 | 判定の手がかり | テンプレート |
|------|--------------|-------------|
| 新機能実装 | 「作って」「追加して」「実装して」 | [templates/feature.md](templates/feature.md) |
| バグ修正 | 「直して」「エラーが出る」「動かない」「おかしい」 | [templates/bugfix.md](templates/bugfix.md) |
| リファクタリング | 「整理して」「きれいにして」「分割して」（振る舞い不変） | [templates/refactoring.md](templates/refactoring.md) |
| コードレビュー | 「レビューして」「見て」＋対象が diff/PR/コード | [templates/code-review.md](templates/code-review.md) |
| 設計レビュー | 「レビューして」「評価して」＋対象が設計・提案・文書 | [templates/design-review.md](templates/design-review.md) |
| 既存コード調査 | 「調べて」「どうなってる」「どこにある」（変更しない） | [templates/investigation.md](templates/investigation.md) |
| プロトタイプ | 「試したい」「検証したい」「プロトタイプ」「PoC」「まず動くもの」 | [templates/prototype.md](templates/prototype.md) |
| 委譲・オーケストレーション | 「Sonnetにやらせて」「委譲して」、実装をサブエージェントへ切り出す時 | [templates/delegation.md](templates/delegation.md) |

- 複合タスク（例: 調査してから実装）は、種別ごとに分解して**順に**実行する（調査→実装の順で各テンプレートを適用）。
- どれにも当てはまらない場合は、最も近い種別を選んで宣言し、合わない手順はスキップ理由を添える。
- **問題の報告・質問だけで、修正を依頼されていない場合**（「このエラー何？」「CIが落ちてる」）: 既存コード調査として**原因診断まで**を成果物とし、修正はユーザーが求めてから着手する（勝手に直さない）。
- 依頼が過去の文脈を前提とする場合（「昨日の続きをやって」等）: 記録（タスクリスト・開発日誌・git log・会話履歴）から文脈を復元し、「〜の続き＝〜をすることと解釈した」と宣言してから種別を判定する。
- 境界ケースの目安: 「たまに落ちるテスト」→ バグ修正（再現の工夫が要る旨を宣言）/ 性能改善 → 新機能実装に準じる（計測を完了条件に足す）/ 「調べて直して」→ 調査 → バグ修正の順で分解 / テストだけの追加 → 新機能実装に準じる（実装済みの振る舞いを仕様として固定）。
- 委譲モードは他モードと**組み合わせて**使う（例: 実装を委譲するなら、feature.md の完了条件を委譲プロンプトの完了条件に転記する）。

### 2. 該当テンプレートを Read する

判定した種別のテンプレートファイルを **必ず Read してから** 作業を開始する。
テンプレートには「着手前に揃える情報 / 作業手順 / 完了条件」が定義されている。

### 3. 着手前に情報を揃える

テンプレートの「着手前に揃える情報」を確認し、欠けているものは
[protocol.md](protocol.md) §0 の判断フローで扱う：

- コードベース・履歴・実行で分かるもの → **自分で調べて埋める**
- 仕様の価値判断・ユーザーにしか分からないもの（症状の詳細、期待動作、検証したい仮説など） → **まとめて一度に質問する**（小出しにしない）

### 4. テンプレートの作業手順を実行する

- 手順の順序を守る（例: バグ修正なら「再現 → 原因特定 → 回帰テスト → 修正」。順序に意味がある）。
- 作業中も共通プロトコル（都度検証・2ストライクルール・スコープ規律）を維持する。

### 5. 完了条件と突合して報告する

- テンプレートの「完了条件」チェックリストを1項目ずつ確認し、**満たせなかった項目は正直にそのまま報告**する。
- 報告は4部構成（結果 / 変更点 / 検証 / 未検証・仮定・提案）。

## 注意

- テンプレートを読まずに「だいたいこの流れ」で進めない。手順の省略は品質劣化がユーザーに見えない形で起きる。
- **既存のエージェント運用ルール（`~/.claude/rules/agents.md` の planner / tdd-guide / code-reviewer 等）とは役割が異なり矛盾しない**: fable5 は「何をどの順で満たすか」（手順と完了条件）、エージェントは「誰がやるか」（実行主体）。テンプレートの手順の中でエージェントを使ってよい（例: feature.md の計画フェーズで planner、完了前に code-reviewer、実装の切り出しに delegation.md）。
- このスキルは vault の `50_Investigations/Fable5思考フレームワーク.md` ノート群の実行形。テンプレートを改善したら vault ノート側にも反映を提案する。
- 運用中に観察した失敗パターンは `50_Investigations/Fable5モデル移行ガイド.md` の表への追記を提案する。
