# Gitコミット

## 範囲とブランチ

自然言語の依頼と引数から範囲を決める。コミットだけの依頼はコミットまで、`--push` はpushまで、`--pr` はpushとPR作成まで。既存コミットのpushだけを求められた場合は、新しいコミットを作らない。

`git status --short`、`git diff --stat`、`git diff --cached --stat`、`git branch --show-current`、`git log --oneline -5` を確認してから、対象の差分を読む。

`main` / `master` / `develop` / `development` への直接コミットが明示されていなければ、現在のHEADから作業ブランチを作成する。名前は変更目的から決める。指定ブランチがある場合は尊重する。切り替えが既存差分と衝突する場合やdetached HEADの扱いが不明な場合は確認する。

## ステージングとコミット

- 独立した目的ごとに分ける。同じ変更の実装とテストは一緒にする。
- ユーザーの既存差分・ステージ済み変更を勝手に取り込まない。対象が混在して分離できなければ確認する。
- `git add -- <対象ファイル...>` で対象を指定し、`git diff --cached` で実際のコミット内容を確認する。必要なら変更箇所単位でステージする。`git add -A` は使わない。
- リポジトリ指定の検証を行う。失敗を隠したりhookを迂回したりしない。
- Conventional Commitsで目的を簡潔に記述する。日本語の要約も可。固定のモデル名、架空の共同著者、生成ツールの署名は付けない。明示された署名規約がある場合はそれに従う。
- 複数行のメッセージは一時ファイルに書き、`git commit -F <file>` で渡す。依頼なしに amend や履歴の書き換えを行わない。

## PushとPR

依頼された場合のみ実行する。既存のupstreamを確認し、未設定ならリポジトリのリモートを確認して `git push -u <remote> <branch>` を使う。複数リモートで送信先が曖昧なら確認する。force pushは行わない。

PRは既存PRとリポジトリのテンプレートを確認し、変更後の挙動と実行した検証を記述する。本文を一時ファイルに書き、`gh pr create --base <base> --title <title> --body-file <file>` で渡す。引数はシェル用にクォートする。未実行テストを成功扱いにしない。

最後に `git status --short` と作成したコミットを確認し、コミットID、ブランチ、push結果、PR URLを該当する範囲で報告する。失敗時は完了済み操作と残件を区別する。
